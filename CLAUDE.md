# next-gen-analytics

A private small-company analytics stack: model2data + three public APIs → dlt → MotherDuck →
dbt + MetricFlow → a Claude dashboard and Claude answers, run daily by Orchestra. It is the
small-company variant of the house stack; the account-free reference is `reference-architecture`
(DuckDB + Evidence).

## Commands

```bash
uv sync --extra dev
uv run poe check                                  # ruff + ty + pytest; must be green before a commit
NGA_DESTINATION=duckdb uv run nga run             # whole stack locally, no account
uv run nga transform build -s +fct_orders         # extra args pass through to dbt
DBT_TARGET=prod uv run nga metrics query --metrics orders --group-by metric_time__month
DBT_TARGET=prod uv run nga dashboard-sql          # after any change to a metric the dashboard uses
```

## Layout

- `source_system/noordkust.dbml` is the shop's source system. `nga/generate.py::align_source` fixes
  what DBML cannot express.
- `nga/pipelines/` has one dlt module per source. Raw schemas: `raw_noordkust`, `raw_open_meteo`,
  `raw_frankfurter`, `raw_nager_date`.
- `dbt/` holds the dbt project. Marts carry the MetricFlow semantic models and metrics.
- `dashboard/queries/` holds the SQL the KPI dashboard runs live, compiled by MetricFlow
  (`nga/dashboard.py`). Generated: never edit by hand.
- `dashboard/artifact/` is a backup of the dashboard itself (page, data sources, title). After any
  change to the dashboard, export it here and commit; `dashboard/README.md` says how.
- `.claude/skills/answering-with-metricflow/` is how Claude answers data questions here.
- `charts/` is the dbt Charts board (`docs/dbt-charts.md`); `lightdash/` and `docs/lightdash.md`
  are the Lightdash route. Both are alternative front ends on the same marts.
- `docs/architecture/` holds two diagrams (JB Analytica diagram-design skin): `diagram` (this stack)
  and `front-ends` (one metric layer, the front end as the client's choice). All `.html`, `.svg` and
  `.png` files are generated by `build.py`: change the drawing there, then run
  `python3 docs/architecture/build.py --export` (any Python with Playwright installed) and commit.
- `docs/orchestra.md` says how the Orchestra pipeline is wired; `docs/versions.md` explains the pins.

## Conventions specific to this repo

- **Metrics are defined once, in MetricFlow YAML**, and every number anyone sees comes from them:
  Claude answers through `nga metrics query`, and the dashboard runs SQL MetricFlow compiled
  (`dashboard/queries/`). After changing a metric the dashboard uses, run `nga dashboard-sql`,
  commit the diff, and set the new SQL as that dataset's query in the dashboard, unchanged.
- **Every stage is one Orchestra task.** CLI commands stay non-interactive, log to stdout, exit
  non-zero on failure and work from a fresh clone: `load shop` generates first when needed.
- **Sources carry freshness from `_dlt_load_id`** and marts carry `build_after`; Orchestra's
  state-aware dbt runs depend on both. Keep them when adding a source or a mart, and keep dlt
  lists as JSON columns rather than child tables, which have no `_dlt_load_id`.
- **Dev and prod write different schemas** (`nga_dev_*` vs `nga_*`): Orchestra keys dbt state by
  table name, so a shared schema would let one environment skip the other's rebuild. Answers and
  the dashboard read prod (`DBT_TARGET=prod`).
- **"Revenue" means realised revenue**: not cancelled, not returned, shipping excluded. Money is
  minor units in the order currency at the source and EUR in the marts, converted at the ECB
  rate on or before the order date.
- dbt source names have no underscores (`openmeteo`, `nagerdate`), because the house
  `stg_<source>__<table>` naming rule allows none. The raw schemas keep theirs.

## Gotchas

- **The dbt Charts board repeats metric logic in its own SQL** (dbt Charts reads the marts, not
  MetricFlow). When a metric in `_marts__metrics.yml` changes, change `charts/noordkust_kpis.yml`
  too, then `dct validate --strict`.
- **Keep a metric's filter on its own semantic model.** Lightdash's MetricFlow translator skips a
  filter that uses another model's dimension (`product__category` on an order-line metric). Put
  the column on the fact instead, as `fct_order_items.product_category` is. Then check that
  `lightdash compile --verbose` still reports all 29 translated; see `docs/lightdash.md`.

- **`mf` does not parse the dbt project**: it reads `dbt/target/semantic_manifest.json` as the last
  dbt command left it, which names that run's warehouse. `nga metrics` and `nga dashboard-sql`
  run `dbt parse` first; calling `mf` directly after a local run queries the wrong database.
- **The MotherDuck connector answers with rows as arrays** (`{columns, columnTypes, rows}`), and a
  HUGEINT (`SUM` of an integer) comes back as text. The dashboard page has a loader that zips
  rows with columns and types numbers; a new dataset needs its id added to that loader.
- **Never use a cross-table `after` hint in the DBML**, even though `model2data validate`
  suggests one. model2data draws the child's date first and then only parents older than it
  qualify, so items piled onto the earliest orders and revenue fell about 85% over the year.
  `align_source` sets those dates instead, and `tests/test_dbml.py` allows exactly those warnings.
- **`MOTHERDUCK_TOKEN` is required unless `NGA_DESTINATION=duckdb`.** The local DuckDB file
  takes one writer at a time, so run `load` and `transform` in sequence there. On MotherDuck the
  four loads can run in parallel.
- **The preflight workflow is manual only.** dbt-preflight can fixture only the shop DBML, not the
  three API sources.
- **sqlalchemy is pinned below 2.0.55**, and dbt-core below 2; see `docs/versions.md`.
